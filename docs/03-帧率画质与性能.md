# 03 帧率、画质与性能调参

## 三层参数

| 层 | 参数 | 生效方式 |
|---|---|---|
| iPad 广播扩展 | 长边 px / JPEG 质量 | 每帧先拉 `/status` 的 `qse`/`qql`，运行时改免重装 |
| 固件 | `fps`（期望帧率）/ 广播节流 | `/config?fps=` 即时下发 |
| 控制台 | 轮询节奏 | 新帧 60ms 内追拉；无新帧 clamp(900/fps, 250, 1000)ms |

改法：网页直接开 `http://<esp32-ip>/config?token=...&edge=560&q=32&fps=2`
（edge=JPEG 长边上限，q=质量）。20 秒内扩展跟随，**全程免重装**。

## 服务器容量模型（ESP32 单线程）

ESP32 的 HTTP 服务器单线程，容量约 **1.0 秒工作量/秒**：

- 收 73KB 上传 ≈ 0.7s（@105KB/s）
- 发整图 ≈ 0.3s（@245KB/s）
- **帧体积是第一变量**：暗页 ~21KB，游戏亮色页 ~90KB。帧体积 × 2 层收发 > 1s 就开始积压卡顿。

实测稳定组合：

| 场景 | edge/q/fps | 帧体积 | 实测帧率 |
|---|---|---|---|
| 文档/桌面 | 900 / 50 / 1 | ~40KB | ~1fps |
| 游戏/亮色 | **560 / 32 / 2** | 33KB | **1.6fps 稳定** |
| 游戏（备选） | 640 / 35 / 2 | 43KB | 偶发积压 |

## 调参思路

1. 先看 `/status` 的 `upok`（成功上传数）与 `upfail`（失败数）：**健康=upok 持续涨且 upfail=0**。
2. `fid ≈ upok` 说明图床在收；控制台 `fid` 不涨 = 拉帧链路问题（先查 token/网络）。
3. 卡顿先**查帧体积再动别的**：`shot` 字段 KB 变化即帧体积。体积大→降 edge/q；
   `fps` 是节流上限，降 fps 不能降体积。
4. **不要调 socket 超时**：被 iOS 节流的上传会被更短的超时切断，形成重试循环
   （实测有害，已永久回滚）。卡顿永远优先降帧体积。

## 延迟预算

实测端到端 ~0.7-1s：广播管道(系统内部缓冲) ~0.3s + 上传 ~0.3s + 轮询间隔 ~0.25s。
对"看着画面点按钮"的用途足够；游戏内实时操作不是本设计目标。

## 已知平台约束（无解，别浪费时间和它们搏斗）

1. 广播不能静默自启：iPad 每次重启后要人点一次「开始广播」。
2. 广播运行时顶部有红色胶囊指示（系统强制）。
3. 免费签名 7 天过期，过期重签（数据不丢）。
4. 扩展的 ESP32 地址/令牌是编译期常量（改 IP 要重编译）；帧参数运行时可调。
